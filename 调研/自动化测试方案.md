# 自动化测试页签：可行性分析与实施方案（第 3 版）

> 状态：方案基本定稿，**未动工**。第 9 节的 POC 准备项到位后开始 POC。
> 日期：2026-11-06（第 2 版根据第一轮答复修改；第 3 版根据第二轮答复修改：建单处理人、Unity 版本、执行器支持 Mac、客户端由 Claude 承担）

## 0. 名词解释

- **执行器**：装在测试同学电脑上的一个小程序，装一次、开机后在后台运行。浏览器出于安全限制不能直接打开本机的 Unity 或操作手机，所以需要它做“本地的手”：平台上点“执行”后，任务发到这台电脑的执行器，执行器调起本机的 Claude Code 去 Unity / 手机上跑用例，再把结果和截图传回平台。测试日常只在平台上点按钮，不用碰它。
- **POC**（概念验证）：正式开发前，先花 1 周用真实材料小规模试一遍最没把握的环节（比如真机上 Claude 能不能稳定点准按钮），拿到成功率、耗时、额度消耗的数据，再决定正式方案怎么做，避免做完才发现走不通。

## 2. 结论

**能做。三个环节难度不同：生成用例和自动建单把握大，Unity 编辑器执行把握较大，安卓真机执行要靠 POC 验证。**

| 需求 | 可行性 | 主要难点 |
| --- | --- | --- |
| ① 生成测试用例 | 高 | 原型链接要先导出；生成结果要测试审核 |
| ② 编辑器执行 | 中高 | 需要往工程里加一个**只在编辑器里生效**的 Unity MCP 插件（不会进安装包） |
| ② 安卓真机执行 | 中，待 POC | Unity 界面是游戏自己画的，系统读不到按钮，只能截图识别坐标；成功率不够时需要在测试包里接测试 SDK |
| ③ 失败自动建单 | 高 | AI 误判会把假问题直接发给开发，必须复跑确认 + 去重 |
| 额度 | 待 POC | 每条用例都会消耗执行者的团队版额度，真机每步截图消耗更多，批量跑可能触发用量上限 |

## 3. 总体架构

```
┌──────────── 缺陷平台（腾讯云）─────────────┐
│ 自动化测试页签：用例库 / 执行记录            │
│ 服务端：用例与执行 API、执行器在线状态、任务下发 │
│ 已有：APP 提单接口 POST /api/v1/app/defects  │
└──────────────▲────────────────────────────┘
               │ HTTPS（执行器主动连平台取任务、传结果；电脑不需要公网 IP）
┌──────────────┴──── 测试同学的电脑（Windows / Mac）──────┐
│ 执行器（后台小程序，用个人 Token 连平台）                 │
│   └─ 调起本机 Claude Code（团队版账号登录，无界面模式）    │
│        ├─ 平台 MCP：读用例、写结果                          │
│        ├─ Docs 工具：读 claude.ai 文档链接（生成用例时）     │
│        ├─ Unity MCP：进 Play 模式、点 UI、读 Console、截图  │
│        └─ adb：真机截图、点击、滑动、logcat                 │
│   失败 → 复跑确认 → 调 APP 提单接口建单                      │
│ Unity 编辑器 + 工程        USB 连接的安卓手机                 │
└──────────────────────────────────────────────────────┘
```

- **Claude 只在本机运行**，用的是执行者自己的团队版账号，平台服务器不存任何 Claude 凭据。
- 谁在平台上点“生成”或“执行”，默认就在谁的电脑上跑；也可以选其他在线的电脑（比如专门接手机的那台）。
- 本机需要安装 Claude Code 命令行版，并用团队版账号登录一次（当前这台电脑只有桌面 App，还没装命令行版）。

## 4. 三项能力的具体做法

### 4.1 生成测试用例

1. 测试在平台上贴文档链接，或上传导出的原型 HTML，可补充说明、选择模块。
2. 点“生成用例”，任务发到本人电脑的执行器；Claude 读材料，按固定格式输出用例，写回平台。
3. 平台显示草稿，**测试逐条审核、修改后入库**；同一份需求重新生成时只追加新用例，不覆盖已审核的。

每条用例的字段：

| 字段 | 说明 |
| --- | --- |
| 标题、模块、优先级 | 模块对应平台已有的模块，用来决定建单处理人 |
| 前置条件、步骤、预期结果 | 步骤写成可操作的句子，AI 和人都按它执行 |
| **测试数据** | 每次输入的值，如昵称“空 / 1 个字 / 20 个字 / 21 个字 / emoji”。测试可以随时改或加几组边界值，AI 和人工执行同一份 |
| 执行方式 | `自动` / `人工`，人工时写原因（硬件、语音、真实响铃、主观体验等） |
| 适用环境 | 编辑器 / 真机 / 都可以 |
| 来源 | 对应文档哪一节（可点开原文） |

### 4.2 执行测试用例

测试在用例库勾选用例 → 点“执行” → 选环境（我的电脑上的 Unity 工程，或某台电脑上连着的某台手机）。

执行器逐条处理（每条用例单独一次 Claude 会话，互不影响）：

1. 准备环境：编辑器进入 Play 模式；真机启动 APP、清空 logcat。
2. Claude 按步骤和测试数据操作，每步截图。
3. 判断结果并写回：`通过` / `失败` / `存疑`（文案差异、主观表述、实现与需求文档不一致等需要人判断的，POC 中 10 条有 3 条属于这类）/ `阻塞`（环境问题，如手机掉线、编辑器编译报错）/ `转人工`（按钮找不到、需要验证码等，并写明卡在哪一步）。每条用例同时截取执行时段的 Console / logcat 错误一并判断（POC 中唯一的疑似真缺陷是从日志发现的）。
4. 标了“人工”的用例不派给 Claude，直接列在执行记录的“待人工执行”里；测试手动做完在同一页面填结果，失败可一键建单（同样走 APP 提单接口）。

| 环境 | 驱动方式 | 前提 |
| --- | --- | --- |
| Unity 编辑器 | [MCP for Unity](https://github.com/CoplayDev/unity-mcp) 插件：控制 Play 模式、读 Console、执行编辑器操作；插件不足的部分（按物体路径点击 UI、截 Game 视图）由 Claude 写一个仅编辑器生效的小工具补上 | **工程里已有该插件**，无需安装；本机已有 Python 和 uv。每个要跑编辑器用例的测试需要本地有工程 |
| 安卓真机 | adb 截图 → Claude 看图给坐标 → adb 点击 / 滑动；日志用 logcat | 手机开 USB 调试，电脑装 adb（Windows / Mac 都有官方 platform-tools；这台电脑已有 Android Studio，自带 adb） |
| 安卓真机 · POC 结论 | 已验证可行（10 条约 6 分钟）。需补：测试机装 ADB 输入法以输入中文；每次点击后重新截图确认，防止布局变化后点偏；测试包打开 Unity 日志或取 App 自带日志 | 见 `调研/POC/POC 结果（真机部分）.md` |
| 安卓真机（POC 不达标时） | 测试包接入 AltTester 或 Poco，Claude 按名字找按钮 | 客户端改动，只放测试包；AltTester 是 GPL-3.0，官方说明仅内部测试使用没有分发义务，正式包不能带 |

安全：执行器里的 Claude 只开放上面这些工具，不允许改工程文件、不允许执行任意命令。

### 4.3 失败自动建单（走 APP 提单接口）

用例判为失败后（`存疑` 不自动建单，由测试在执行记录里确认后一键建单）：

1. **复跑确认**：同一用例自动再跑一次，两次都失败才建单；一次过一次不过记为“不稳定”，只记在执行记录里，不建单。避免 AI 误判直接打扰开发。
2. **去重**：同一用例在未关闭缺陷里已有记录时，不重复建单，只在执行记录里关联原单。
3. 调用 `POST /api/v1/app/defects`，字段对应如下：

| 接口字段 | 填什么 |
| --- | --- |
| `appId` | 项目已绑定的 APP 标识（项目设置里选一个） |
| `reportId` | 每条“执行记录 × 用例”固定一个 UUID，网络重试不会重复建单 |
| `title` / `description` | 用例标题 + 实际现象；描述里写预期与实际、执行环境、执行记录链接 |
| `steps` | 用例步骤 + 本次用的测试数据 |
| `severity` | 由 Claude 按影响判断（崩溃 / 卡死为严重，界面问题为一般） |
| `reporterName` | 点执行的测试 |
| `ownerNames` | 被测分支的创建人（见下方「处理人怎么算」）；找不到时不传，接口按项目默认处理人指派 |
| `appVersion` / `appBuild` / `deviceModel` / `osVersion` | 真机从 adb 读取；编辑器填 Unity 版本和工程分支 |
| `page` | 出问题的界面 |
| `extra` | `{"source":"autotest","caseId":…,"runId":…}`，平台据此在缺陷详情显示“来自自动化测试”并能跳回执行记录 |
| `files` | 失败步骤及前 2 步截图、日志（编辑器 `Editor.log` 截取执行时段 / 真机 logcat），可选录屏 |

接口已有的能力直接生效：日志摘要自动提取、录屏抽帧、处理人通知、按 `reportId` 幂等。

**处理人怎么算（被测分支上的第一个提交的作者）**

1. **确定被测分支**：编辑器执行时取本地 Unity 工程的当前分支；真机执行时包里看不出分支，由测试在点“执行”时从 GitHub 分支列表里选（平台记住上次的选择）。
2. **找第一个提交**：在被测分支上、但不在 `origin/prod` 上的提交里，取最早的一个，它的作者就是分支创建人。
   - 编辑器执行：执行器在本地工程里用 git 直接算。
   - 真机执行：测试电脑上不一定有工程代码，由平台调 GitHub 的比较接口算（`prod...被测分支`）。这需要在项目设置里填一个对 `bud-technologies/BudBox` 只读的 GitHub 访问令牌。
   - 实测：当前分支 `cn_1.0.2_mobai` 与 `cn_1.0.2` 内容相同，相对 `origin/prod` 有 141 个提交，最早的一个是 Mabel0521（chenboya@pointone.tech，10-28），按规则提给他。**但这 141 个提交来自 4 个人**（Mabel0521 64 个、liuhe330 57 个、boli 15 个、luyueke 5 个），见第 9 节问题。
3. **对应到平台用户**：按提交邮箱匹配平台用户的邮箱（提交里是公司邮箱，如 `chenboya@pointone.tech`；Git 用户名如 `Mabel0521` 与平台姓名对不上，不能只靠姓名），匹配不上再按姓名匹配，得到的平台姓名作为 `ownerNames` 传给接口。
4. **多人分支按改动找作者（已定，方案 B）**：被测分支相对 `origin/prod` 只有一位作者时，直接用第 2 步的结果；有多位作者时：
   1. Claude 根据失败用例的功能和日志（报错堆栈里的类名、界面名），在分支的改动文件里找出相关的代码文件；
   2. 取这些文件在 `origin/prod..被测分支` 范围内最近一次提交的作者作为处理人；
   3. 找不到相关文件或判断不准时，退回第 2 步的“第一个提交的作者”；
   4. 缺陷描述里写明处理人是怎么定的（如“按 `AlarmPanel.cs` 最近提交者 liuhe330 指派”），方便被指派的人判断是否转派。
5. **兜底**：被测分支就是基准分支本身、分支上还没有新提交，或作者匹配不到平台用户时，不传 `ownerNames`，按项目默认处理人指派，并在描述里写明“分支 xxx，首个提交作者 xxx（未匹配到平台用户）”。

## 7. 主要风险

1. **团队版额度**：自动执行消耗执行者个人额度，批量跑可能触发用量上限，POC 实测后定每天的执行规模。
2. **真机识别**：截图识别坐标的准确率和速度是最大不确定项。
3. **AI 误判直接到开发**：靠复跑确认和去重减少误报；POC 统计误判率，偏高就改成先进“待确认”状态。
4. **原型链接**：Claude Design 链接需导出才能用，12-14 并入 Claude 后改用 artifact 链接。
5. **执行时占用电脑**：编辑器执行期间 Unity 被占用，建议用专门的电脑或下班后执行。

iOS、测试计划与进度报表、定时自动回归、服务端调用 Claude。
